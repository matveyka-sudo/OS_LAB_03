## Начни с этого

Открой рядом main.c и этот файл. Сначала запусти пример `tests/three.txt`.
Получится x=(2,3,-1). Пройди вручную одну операцию вычитания строк и объясни,
почему уравнения после неё имеют те же решения. Потом разбери `eliminate`,
`worker_main` и ветку синхронизации в `gauss`. Это основа защиты.

## Что решается

Система линейных уравнений — несколько равенств с общими неизвестными.
Например 2x+y=5 и x-y=1. Ответ x=2, y=1 удовлетворяет обоим равенствам.
В записи Ax=b матрица A хранит коэффициенты, x — неизвестные, b — правые части.
В программе всё записано в расширенную матрицу [A|b], то есть N строк
по N+1 числу. Последний столбец — b. Данные имеют тип double.

Метод Гаусса сначала делает нули под диагональю (прямой ход), затем находит
неизвестные с конца (обратный ход). Вычитание из строки другой строки,
умноженной на число, не меняет множество решений.

На шаге k коэффициент для строки i: `factor = a[i,k] / a[k,k]`.
Для j=k+1..N: `a[i,j] -= factor * a[k,j]`. Последний столбец тоже меняется.
`a[i,k]` сразу записывается равным нулю. Пустые столбцы слева уже не трогаем.

После прямого хода последнее уравнение содержит только последнюю неизвестную.
`x[i] = (b[i] - сумма(a[i,j]*x[j], j>i)) / a[i,i]`.
Цикл i идёт от N-1 к 0: нужные x[j] уже вычислены.

## Главный элемент и ограничения численной точности

В столбце k выбирается максимальный по модулю элемент среди строк k..N-1.
Его строка меняется местами с k-й. Это **частичный выбор главного элемента**.
Он выполняется всегда, даже если прежний элемент ещё не близок к нулю.
Так мы избегаем деления на ноль и часто уменьшаем влияние округлений.

Порог `DBL_EPSILON * N * scale`, где scale — максимальный модуль коэффициента
исходной A, без столбца b. DBL_EPSILON — расстояние от 1 до следующего
представимого double (около 2,22e-16). Порог зависит от масштаба: система,
умноженная на 1e-100, не отбрасывается только потому, что числа малы.

Если ведущий элемент не конечен или не больше порога, функция сообщает
об отсутствии безопасного единственного решения. Это может означать
вырожденность, несовместность или численную проблему. Код **не различает**
эти причины и не вычисляет ранг/число обусловленности. Очень разномасштабную,
но обратимую матрицу порог тоже может отклонить. Это ограничение нужно назвать.
Числа с переполнением и NaN не являются правильными ответами.

## Память и индексы

`malloc` выдаёт участок памяти в куче, `calloc` ещё заполняет его нулями,
`free` освобождает. При неудаче выделения проверяется NULL.
Массив a одномерный: элемент строки i, столбца j расположен по индексу
`(size_t)i * (n+1) + j`. Здесь 0<=i<n, 0<=j<=n. Последний допустимый
индекс — n*(n+1)-1. Тип size_t нужен для размеров и индексов памяти.

Есть два массива матрицы: рабочий a меняется методом Гаусса, original хранит
исходную систему для проверки. x содержит n ответов. Матрицы требуют примерно
`2*n*(n+1)*sizeof(double)` байт: при n=1000 около 15,3 МиБ. Массивы pthread_t
и Worker маленькие, но каждый дополнительный поток требует также стек ОС.
Автоматические переменные разных потоков лежат на разных стеках; матрица общая.

`goto cleanup` ведёт к одному месту освобождения памяти, чтобы не дублировать
пять free во всех ветках ошибок. Прыжок к bad_args выводит ошибку аргументов.
Это обычный приём процедурного C, рекурсии и объектов C++ в программе нет.

## Поток, процесс и pthread

Процесс — запущенная программа со своим адресным пространством и ресурсами.
Потоки — несколько последовательностей выполнения внутри одного процесса.
У них общие данные и открытые файлы, но свои стеки и состояние исполнения.
Они могут одновременно работать на разных ядрах процессора.

pthread — POSIX-интерфейс управления потоками. `pthread_create` запускает
новый поток с функцией `worker_main` и указателем на его Worker.
Возвращает код ошибки, а не выставляет errno, поэтому используется strerror.
`pthread_join` ждёт завершения конкретного потока и освобождает его ресурсы.
В этой программе join вызывается **в конце**, а не после каждого шага.
Ожидание шагов сделано через mutex, cond и done.

Mutex — замок для согласованного изменения общих управляющих полей.
`pthread_mutex_lock` захватывает его, unlock освобождает. Расчёт строк идёт
**без замка**: иначе параллельные вычисления стали бы последовательными.

Condition variable — условная переменная для сна до изменения состояния.
`pthread_cond_wait` атомарно отпускает mutex и засыпает. Перед возвратом
она снова захватывает mutex. Поэтому основной поток может получить этот же
замок, пока рабочие спят. Wait обязательно находится в while: пробуждение
может быть ложным, а состояние нужно перепроверить.

`pthread_cond_broadcast(work)` будит всех рабочих, когда появился новый шаг
или завершение. `pthread_cond_signal(finished)` будит main после последнего
рабочего. Значение cond не хранит «событие» навсегда: настоящее условие хранится
в полях generation/done/stop. Поэтому сигнал, пришедший до wait, не теряется:
поток сначала проверит нужный предикат и не станет спать.

## Структуры именно нашего проекта

Pool: указатель a, n, фактическое threads; k — текущий шаг;
generation — номер опубликованного задания; done — сколько рабочих закончили;
stop — требование завершить работу; mutex; cond work и finished.

Worker: указатель на общий Pool и свой id. Main имеет id=0, рабочие id=1..p-1.
Поля a/n/threads устанавливаются до создания потоков и больше не меняются.
Управляющие k/generation/done/stop читаются и меняются под одним mutex.
Локальные seen и k в worker_main принадлежат конкретному рабочему.

## Как проходит один шаг

1. На старте все рабочие ждут новое generation под cond work.
2. Main выбирает pivot и при необходимости меняет строки. Предыдущий шаг
   уже полностью закончен: рабочие не пишут матрицу.
3. Main берёт mutex, записывает k, сбрасывает done, увеличивает generation,
   будит рабочих и отпускает mutex.
4. Каждый рабочий замечает новое generation, запоминает k, отпускает mutex
   и вызывает eliminate для своего id. Main одновременно вызывает eliminate(id=0).
5. Рабочий берёт mutex, увеличивает done. Последний сигнализирует finished.
6. Main после своего диапазона берёт mutex и ждёт done==p-1.
7. Только после этого main переходит к следующему pivot.

Номер generation нужен, чтобы отличать новое задание от ложного пробуждения.
Если рабочий поздно запустился или ещё не успел заснуть, он увидит новое
значение и всё равно выполнит шаг. Main не может опубликовать ещё один шаг,
пока не получит done от каждого рабочего.

## Как делятся строки: пример

`rows=n-k-1`, `start=k+1+rows*id/p`, `end=k+1+rows*(id+1)/p`.
Интервал полуоткрытый [start,end). Целочисленное деление отбрасывает дробь.
Например n=10, k=1, p=4: осталось 8 строк с индексами 2..9.
Main получает [2,4), id=1 — [4,6), id=2 — [6,8), id=3 — [8,10).
Если строк не кратно p, размеры отличаются максимум на одну строку.
Если строк меньше p, некоторые диапазоны пусты, но эти рабочие всё равно
сообщают о завершении. На последнем шаге исключение вообще не запускается.

## Почему нет гонки данных

На одном шаге диапазоны не пересекаются. Рабочие не меняют ведущую строку,
а main переставляет строки до публикации задания. Следующий шаг начинается
после done==p-1 и окончания диапазона main. Публикация и приём задания,
а также подтверждение завершения проходят через тот же mutex: он обеспечивает
видимость записей между потоками, а не только взаимное исключение счётчика.
Матрица не нуждается в отдельном mutex на каждую строку.
TSan прошёл тесты, но главное объяснение — именно это разделение данных
и порядок доступа. Тест сам по себе не доказывает корректность всех программ.

Нельзя сразу считать все k одновременно: ведущая строка для k+1 ещё должна
получиться после предыдущего исключения. Параллельны строки **одного шага**.
Обратный ход последовательный: x[i] зависит от уже вычисленных x[j], j>i.

## Ограничение числа потоков

`actual=min(--threads,n)`. Создаётся actual-1 pthread, плюс уже существующий main.
Дополнительных менеджеров потоков нет. Поэтому при --threads 4 максимум 4
потока процесса, а при --threads 1 — только main. При n=3 и лимите 8 создаются 3.
Во время прямого хода main тоже считает строки; при последних шагах часть
участников простаивает. В эксперименте n>=100, поэтому p равен аргументу.

Демонстрация на Mac из корня проекта:

```sh
./build/OS_Lab3_Variant10 --size 1000 --threads 4 --demo 20 &
pid=$!
ps -M -p "$pid"
wait "$pid"
```

Считай строки после заголовка ps. В демопаузе рабочие спят, после неё тот же
набор потоков выполняет решение. Пауза не входит в замеры.
На Ubuntu аналог — `ps -T -p "$pid"`; здесь он не проверялся.

## Все функции main.c

Номера строк относятся к финальной версии. После изменений кода проверь их заново.

### check_pthread (строка 25)

Аргументы: error — код pthread, name — имя операции. Возвращаемый тип void.
Если error=0, ничего не делает. Иначе fprintf печатает strerror(error),
exit завершает процесс с ошибкой. Её вызывают все обёрнутые pthread-операции,
кроме create, для которой есть отдельная ветка частичного завершения набора.
Это не обработчик исключений и не функция errno.

### help (строка 32)

Без аргументов, void. Вызывает puts со справкой, поясняет ключи и границы.
Вызывается main при единственном аргументе --help.

### number (строка 42)

Аргументы: строка s и верхний limit. Возвращает число 1..limit либо 0 при ошибке.
Сбрасывает errno, вызывает strtol, проверяет переполнение, наличие цифр,
конец строки и диапазон. Используется main для ключей и N из файла.
Например «3abc», «-1», «0» и огромное число отклоняются.

### seconds (строка 50)

Без аргументов, возвращает double — монотонное время в секундах.
Вызывает clock_gettime(CLOCK_MONOTONIC), складывает секунды и наносекунды/1e9.
При ошибке perror и exit. Абсолютное значение не является датой: нужна разность
двух вызовов. Смена часов/часового пояса на разность не влияет.

### known_x (строка 59)

Аргумент j — индекс неизвестной с нуля. Возвращает double: j%7-3.
Например -3,-2,-1,0,1,2,3,-3,... Вызывает только арифметику.
Используется generate и verify; эталон не применяется самим решателем gauss.

### generate (строка 63)

Аргументы: выделенный массив a и n. Возвращает void.
Начинает с seed=10. Вложенные циклы заполняют числа от -10 до 10.
uint32_t имеет определённое переполнение по модулю 2^32; поэтому последовательность
воспроизводима и не зависит от реализации rand на разных ОС.
Диагональ заменяется суммой модулей внедиагональных элементов плюс 1:
получается строгое диагональное преобладание. Следующий цикл вычисляет b=A*x_ref,
вызывая known_x. Используется fabs. Система имеет известное единственное решение.

### eliminate (строка 82)

Аргументы: pool — общая матрица и параметры; id — номер участника; k — шаг.
Возвращает void. Вычисляет start/end, получает указатель pivot.
Внешний цикл перебирает только свои строки i. Для каждой вычисляет factor,
ставит ноль в столбце k и внутренним циклом обновляет оставшиеся столбцы и b.
Других функций не вызывает. Самая дорогая часть O(n³) суммарно по всем k.
Её вызывают main через gauss и каждый рабочий через worker_main.

### worker_main (строка 98)

Аргумент void* на Worker, возвращает NULL (void*) после stop.
Приводит указатель к Worker*, получает Pool и свой id. seen сначала равен 0.
Захватывает mutex и в бесконечном цикле ждёт новое generation или stop.
После задания копирует k, отпускает mutex, вызывает eliminate, снова берёт mutex,
увеличивает done и при необходимости сигнализирует finished.
Вновь идёт к проверке условия. При stop выходит из цикла и освобождает mutex.
Вызывает pthread_mutex_lock/unlock, pthread_cond_wait/signal, check_pthread,
eliminate. Память Worker не освобождает: ей владеет main до всех join.

### stop_pool (строка 120)

Аргументы: pool, массив pthread_t ids, число успешно созданных created.
Void. Под mutex ставит stop=1 и делает broadcast(work). После unlock соединяет
все созданные потоки через join. Только затем уничтожает обе cond и mutex.
Вызывает check_pthread для ошибок. Применяется и при обычном завершении,
и если start_pool успела создать лишь часть рабочих. В этом случае
никакого исключения ещё не было; все созданные рабочие получают stop.

### start_pool (строка 132)

Аргументы: pool, массив ids, массив workers, память уже выделена main.
Возвращает 1 при успехе и 0, если create не удалось.
Инициализирует mutex и две cond, затем создаёт threads-1 рабочих.
Каждому задаёт pool и id=i+1. При ошибке печатает strerror и вызывает stop_pool
с числом уже созданных потоков, затем возвращает 0. При p=1 цикл пустой.
Вызывает pthread_*init, pthread_create, check_pthread, fprintf, strerror, stop_pool.

### gauss (строка 149)

Аргументы: pool и выходной массив x. Возвращает 1 при успешном решении либо 0
при недопустимом pivot/не конечном ответе. Меняет a на месте.
Первый двойной цикл находит scale. Внешний цикл k — последовательные шаги.
Вложенный i находит строку best, затем j переставляет полные строки.
Если p=1, непосредственно вызывает eliminate. Иначе публикует задание,
считает диапазон main и ждёт done. В конце обратный двойной цикл находит x.
Вызывает fabs/fmax/isfinite, eliminate, mutex/cond и check_pthread.
Сравнение `k==n-1` прекращает прямой ход после проверки последнего pivot,
потому что ниже уже нет строк. При возврате 0 рабочих корректно завершает main
через stop_pool; gauss сама набором потоков не владеет.

### verify (строка 198)

Аргументы: исходная расширенная a, найденный x, n, признак generated.
Возвращает 1, если проверки прошли, иначе 0. Двойной цикл вычисляет Ax,
невязку, максимальные суммы модулей строк A и нормы b/x.
Для генератора вызывает known_x и оценивает ошибку ответа.
Вычисляет относительную невязку с порогом 1e-10 и ошибку эталона с порогом 1e-8.
Нулевой знаменатель обрабатывает отдельно, переполнение даёт FAIL.
Вызывает fmaxl/fabsl/isfinite, printf/puts, known_x.
Промежуточный long double на Apple arm64 не гарантирует больше точности,
чем double: корректность не опирается на его расширенную точность.

### main (строка 227)

Аргументы argc/argv — число и строки аргументов запуска. Возвращает код процесса:
0 успех, 1 ввод/ресурсы/pthread, 2 нет безопасного единственного решения,
3 проверка ответа не прошла. --help также возвращает 0.
Разбирает пары ключ-значение. Открывает файл, читает N и конечные коэффициенты,
проверяет лишние данные, либо вызывает generate. Выделяет a/original/x/ids/workers,
копирует a в original, запускает pool. Не меняет число потоков по ходу решения.
Если запрошена demo, печатает PID, сбрасывает буфер stdout и спит nanosleep.
Сигнал EINTR может прервать сон: повторяется оставшаяся часть задержки.
Измеряет seconds до и после gauss, останавливает pool, вызывает verify,
для n<=10 печатает ответы. Потом cleanup освобождает все массивы.
Кроме названных функций вызывает strcmp, fopen/fscanf/fclose/ferror, malloc/calloc,
memcpy/free, fprintf/printf/perror, getpid, fflush и nanosleep.

## Как измерялось и что получилось

В Release -O2 таймер охватывает только gauss: прямой ход, его синхронизацию
и обратный ход. Генерация, копирование, создание и завершение набора потоков,
печать, проверка и демопауза исключены. Это **не полное время процесса**.
Для каждого n,p есть один прогрев и 7 запусков. Итог — медиана.
Конфигурации перемешаны; исходные данные для одного n каждый раз одинаковы.

Ускорение `S(p)=T(1)/T(p)`. Эффективность `E(p)=S(p)/p`.
Например n=1000: T1=0,144897 с, T4=0,074512 с, S4≈1,945, E4≈0,486 (48,6%).
При n=100 для 4 потоков S≈0,110: программа медленнее примерно в 9,09 раза.
Для n=600 лучший результат у 2 потоков, для n=1000 — у 4 по медианам.
Разница между 4 и 8 потоками для n=1000 мала на фоне разброса, поэтому
не стоит утверждать, что 4 всегда строго лучше 8 при любой нагрузке.

Маленькой матрице выгоднее один поток: ожидания и пробуждения стоят дороже
самих операций. У больших матриц работы O(n³) становится достаточно.
Но остаются последовательные выбор pivot и обратный ход, ожидания на каждом k,
уменьшение числа строк к концу, общая память и планирование ОС.
CPU M1 имеет 8 физических ядер по sysctl, но число ядер не гарантирует ускорение 8.
Нельзя приписывать весь эффект одному фактору: частоты, размещение потоков
и фоновые процессы в этой работе отдельно не измерялись.

## Ошибки и честные пределы проверки

Проверяются аргументы, чтение, выделение памяти, pthread_create, остальные
pthread-операции, pivot, конечность ответа и невязка. Все выделенные массивы
освобождаются, рабочие завершаются до уничтожения общей памяти.
Санитайзеры ASan+UBSan и TSan прошли по 124 проверки на этом Mac.
Они не заменяют доказательство синхронизации и не гарантируют отсутствие
всех ошибок для любого ввода. Ошибки выделения памяти/create не провоцировались
искусственным исчерпанием ресурсов, но ветки обработки есть и разобраны.
На Ubuntu программу здесь не запускали. Команда наблюдения Ubuntu приведена
для переноса. Дополнительная виртуальная машина не устанавливалась.

## 10 самых вероятных вопросов преподавателя

1. **Что распараллелено?** Обработка разных строк ниже ведущей на одном шаге прямого хода.
2. **Сколько потоков при --threads 4?** Не более четырёх вместе с main; при n>=4 создаётся три рабочих.
3. **Где гонка и как вы её предотвратили?** Потенциально на общей матрице и состоянии шага. Строки разделены, состояние защищено mutex, переход шага ждёт done.
4. **Зачем while у cond_wait?** Чтобы снова проверить предикат после ложного или раннего пробуждения.
5. **Зачем generation?** Отличает новое задание от уже выполненного; без него рабочий может повторить прежний шаг.
6. **Зачем pivot?** Чтобы выбрать ненулевой и достаточно большой по модулю делитель; при необходимости меняются строки.
7. **Почему join не на каждом шаге?** Рабочие живут всю задачу; шаги согласуются cond, а join завершает их в конце.
8. **Почему больше потоков бывает медленнее?** Расходы на синхронизацию, мало строк и последовательные части; реальные числа есть в таблице.
9. **Как проверили ответ?** По исходной A посчитали Ax-b; для генератора ещё сравнили x с заранее известным эталоном.
10. **Как показать потоки?** Запустить --demo 20 в фоне, сохранить $!, выполнить ps -M -p "$pid" на macOS и посчитать строки после заголовка.

## Устный рассказ на 2–3 минуты

В этой лабораторной я решаю систему линейных уравнений методом Гаусса.
Программа написана на C11 и использует POSIX Threads. Она читает систему
из текстового файла либо создаёт диагонально преобладающую матрицу.
Для созданной системы заранее известен ответ, поэтому результат можно проверить.

Матрица хранится в динамическом одномерном массиве. В каждой строке находятся
коэффициенты и свободный член. Сначала выполняется прямой ход: для каждого
столбца выбирается максимальный по модулю ведущий элемент. Если нужно,
строки меняются местами. Затем из нижних строк вычитается ведущая строка,
умноженная на подходящий коэффициент. Так получаются нули под диагональю.
После этого последовательный обратный ход находит неизвестные с конца.

Параллельно обрабатываются разные строки одного шага. Создаётся постоянный
набор рабочих потоков, а основной поток тоже вычисляет свой диапазон.
Ключ threads задаёт общее число потоков вместе с main. Например при значении
четыре создаются три рабочих потока. Каждый меняет только свои строки,
а ведущую все читают. Поэтому записи разных потоков не пересекаются.

Для согласования шагов используются mutex и две условные переменные.
Основной поток публикует номер шага и будит рабочих. Они обрабатывают строки
и увеличивают счётчик завершений. Main начинает следующий шаг только тогда,
когда все участники закончили текущий. Рабочие ждут без активного опроса.
В конце main будит их с признаком stop и вызывает pthread_join.

Ответ проверяется по невязке исходной системы. Я проверил маленькие примеры,
перестановку строк, вырожденные системы, разные размеры и лимиты потоков.
Проверки памяти и гонок санитайзерами прошли. Команда ps на Mac показала
реальное число потоков, соответствующее заданному лимиту.

Производительность измерялась на Mac с Apple M1 и 8 ГБ памяти в Release.
Для каждой конфигурации выполнены семь запусков и взята медиана.
При размере 100 многопоточность замедляет работу, потому что ожидания дороже
вычислений. Для размера 1000 четыре потока дали ускорение около 1,94,
эффективность около 49 процентов. Поэтому увеличение числа потоков полезно
только при достаточном объёме работы и не даёт идеального линейного ускорения.
